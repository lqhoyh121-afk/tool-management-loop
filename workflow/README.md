# T05 workflow 准备说明（阶段一：用例与输入/输出需求）

本文是 #5 派工评论要求的阶段一交付：整理最小正反向用例和流程输入/输出需求。字段、枚举、状态机、错误码、身份命名空间、operation_id 形态、钉钉客户端接口**全部等 contracts（#2）由主控冻结后消费**，本文不定义任何公共概念，出现的阶段名称仅为 design.md 候选主链的语义转述。

依据：#5 全部评论、#2 全部评论（使用者确认的单机 MVP 收口）、SPEC.md、design.md、T01-HANDOFF 及同目录报告、AGENTS.md。

## 范围

按 #2 收口与 #5 派工：一台使用者电脑、一个运行账号、单实例、一套主账（钉钉唯一权威）、一笔完整借还。普通人不进主账，只走受限申请入口；审批明确同意/拒绝；指定管理人分别确认借出和归还。

本卡不做：提醒、延期、部分归还、归还退回、换新、报废、网页平台、跨机并发/迁移、字段级角色矩阵、通用审批框架、自动超时释放。

## 最小用例集

### 正向

- **U1 整笔借还主链**：可信申请 → 明确同意 → 预留成功 → 待借出确认 → 指定管理人真实确认借出 → 借用中 → 原借用关联的整笔归还申请 → 指定管理人真实确认归还 → 库存回读一致 → 关闭。
- **U2 审批拒绝**：明确拒绝后不预留、不发放，单据停在拒绝结果，可追溯；无预留需释放。
- **U3 未借出取消**：仅在尚未借出时，由指定管理人明确提出取消并释放预留；释放后回读可借数量恢复。

### 反向（全部不放行、不推进、不静默降级）

- **R1 错人**：申请人不得以他人身份提交；错人审批不产生同意；错人完成阶段待办不推进状态。
- **R2 缺身份**：无可信提交身份的申请不放行；身份不可由姓名自填补足。
- **R3 错单**：阶段动作与原单关联不匹配时不放行，不串单。
- **R4 数量不足**：超出可借数量不预留、不超借。
- **R5 缺编号**：需追踪的工具缺实物编号时拦截并标待补充，不自动补造、不把记录 ID 冒充实物编号。
- **R6 重复事件**：同一动作的重复扫描、重复事件、重复请求不重复扣减或重复办单。
- **R7 旧阶段/旧事件**：已完成、已取消、已拒绝阶段的后续动作不放行；不同意之后的待办完成回执（T01 实测语义：仅勾完成 ≠ 同意）。
- **R8 结果未知**：外部写入结果未知时挂起并回查精确目标，有证据才续跑，不盲重发、不盲重建。
- **R9 未确认归还**：归还确认前不恢复可借数量、不关闭借用。
- **R10 预留竞争**：并发预留冲突显式挂起，不伪造成功、不超发。
- **R11 重启/部分成功**：跨表部分成功后重启，凭本地运行流水与外部回读恢复推进；本地流水不构成第二套库存主账。

## 各阶段输入/输出需求

输入字段名与错误码【contracts 冻结后填充】；此处只描述语义。每个外部副作用必须绑定稳定 operation_id 并保留写入回执与独立回读证据。

| 阶段 | 需要的输入（契约依赖） | 输出/副作用 | 不放行条件 | 不变量 |
|---|---|---|---|---|
| 申请受理 | 可信提交身份（系统 creator，非自填）、台账引用、工具、数量、预计归还时间；需追踪工具的实物编号 | 申请记录（钉钉主账），关联保存 | R1/R2/R5 | 一单一种可多件；字段不猜造 |
| 审批 | 独立于申请的明确同意/拒绝事件；原单关联 | 审批结果记录；同意→预留核验；拒绝→终态 | R1/R3/R7 | 待办完成 ≠ 同意；结果不能来自勾选 |
| 预留 | 同意结果 + 当前可借数量回读 | 成功预留（数量/编号级）；或冲突挂起 | R4/R10 | 单件不重复预留；冲突显式挂起 |
| 借出确认 | 指定管理人对关联待办的真实完成证据（实际完成者，非执行人声明） | 实际借出记录；可借数量扣减生效 | R1/R3/R7 | 核验实际操作身份后才更新 |
| 借用中 | — | （提醒属 scheduler，本卡不实现） | — | 取消仅未借出时由指定管理人提出 |
| 归还申请 | 原借用关联、整笔数量及编号一致 | 归还记录 + 管理人确认待办 | R3；数量/编号不一致 | 整笔归还，不分批 |
| 归还确认 | 指定管理人真实完成证据 | 台账更新、库存恢复（此时才恢复可借数量） | R1/R9 | 确认前不恢复数量 |
| 回读关闭 | 库存数量/编号/状态精确回读一致 | 借用关闭（终态） | 回读不一致不关闭 | 未回读不得关闭 |
| 取消 | 指定管理人明确取消指令 + 当前未借出 | 释放预留、可借数量恢复并回读 | 已借出不放行 | 不自动超时释放 |

## 对 contracts 的消费需求清单（供 #2 参考，不构成定义）

1. 稳定 operation_id：同一动作跨扫描、跨重启同 ID；幂等判定依据。
2. 业务状态与"操作结果未知"必须可区分，受理成功不得当终态。
3. 身份两命名空间（通讯录 vs 待办内部 ID）映射需有创建及回读证据，禁止直接相等比较。
4. 写入回执 + 独立回读接口语义；T01 实测形态教训：空表 `records:null` 与 `[]` 两形态、`success:true` 不等于业务成功、number 回读为字符串需解析、date 带时区。
5. 预留冲突挂起的状态与恢复语义。
6. 取消的权限与阶段语义（仅未借出、指定管理人、明确指令）。
7. 单实例排他：第二实例启动必须被底层闸门拦截（部署侧实现，workflow 依赖该前提）。
8. 恢复记录的边界：本地运行流水仅用于消费进度、操作意图、任务关联与恢复，不得成为第二业务库存。
